# 規範執行稽核細則

核心原則:規則的內容來自現場的分層檔案,本 reference 只提供萃取、核驗與處置方法。系統、使用者與專案規則的授權邊界高於本 skill。

## 萃取可機械核驗的約定

讀取實際生效的規則鏈時,找出能夠轉成檢查指令的祈使句,並記錄原文出處。

| 類別 | 規則句式 | 核驗證據 |
|---|---|---|
| 命名 | 「目錄必須 kebab-case」 | 同層名稱清單與例外條款 |
| 必備檔案 | 「每個專案必須有 X」 | 檔案存在性與最小內容 |
| 同源 | 「A 符號連結/匯入 B」「只編輯 B」 | `readlink`、realpath、匯入、載入診斷 |
| 安全紅線 | 「密鑰不進程式碼」「ignore 必須含 X」 | tracked files、ignore 規則、secret scanner |
| 目錄紀律 | 「根目錄不放裸檔案」 | 根目錄 manifest 與白名單 |
| 宣告一致 | 「啟動指令/URL/服務名稱必須真實」 | package/config、服務或 live probe |
| 發布流程 | 「完整回報與使用者確認先於清場」 | knowledge receipt、deploy marker、cleanup candidate、post-report user approval receipt |

行為偏好如「結論先行」也要遵守,但除非存在可驗證的範本或門禁,否則不屬於結構稽核的結果。

## 確定實際的規則鏈

不要假設所有平台都從根目錄讀同一份檔案:

1. 辨識目前的 Agent 與 `cwd`。
2. 從專案根目錄到 `cwd`,依序找出本平台的規則檔、override、fallback 與路徑規則。
3. 再查使用者/組織層級的規則。
4. 記錄載入順序與覆蓋關係;同一目錄只採用平台實際會載入的檔案。
5. 若專案宣告 CLAUDE.md/AGENTS.md 必須同源,再核對符號連結或匯入;沒有宣告時只回報分歧風險,不擅自規定方向。

## 核驗範圍

- **目前專案的請求**:稽核目前專案的內容;上層規則與同層名稱只做唯讀檢查。
- **跨專案變更**:稽核實際受影響的 upstream/consumer 文件,先說明擴大範圍的依據。
- **整個 workspace**:使用者明確授權後,逐專案做存在性、同源與規則檢查;仍依風險決定是否讀取全文。
- **全域設定**:預設只唯讀稽核失效引用、矛盾與載入漂移,不把專案細節寫入全域設定。

## 處置等級

先服從現場規則;若現場沒有更具體的規定,用下面的預設分級。

### 可以直接修

必須同時滿足:在請求範圍內、安全、可逆、沒有外部副作用,並且目前規則授權自動修復。例如:

- 現場明確要求的符號連結/匯入缺失;
- `.gitignore` 缺少規則明文要求的敏感檔案模式;
- 文件裡明顯的筆誤、確認已不存在的失效連結;
- 同一事實的過期摘要,可以由目前程式碼/執行狀態唯一裁決。

### 先回報再決定

- 目錄或專案重新命名、檔案/目錄刪除;
- 合併內容不同的規則檔且權威來源無法唯一確定;
- 規則與穩定實務之間出現漂移,但不清楚該改規則還是該改實務;
- 修改範圍外的專案、全域設定或其他人的工作區;
- 停服、權限/密鑰、不可逆的遷移、對外發布等現場規則列出的風險動作;
- 唯一證據存在於未合併/dirty 的 lane 中,清理會導致它遺失。

### 只做唯讀回報

- 使用者明確限定為「看看/稽核/回報」;
- 發現的問題位於請求範圍之外;
- 平台產生的檔案禁止直接修改;
- 事實無法驗證,或需要外部系統的權限。

## 規則本身的品質

同時檢查:

- **失效引用**:路徑、指令、服務、專案是否存在;拿不準跨裝置路徑時不能直接刪除。
- **矛盾**:上下層規則、override、skill 與實務之間是否給出互斥的要求。
- **不可執行**:大量「保持整潔/注意安全」但沒有給出判斷標準。
- **重複**:同一條紅線在全域、專案與 skill 裡複製,導致未來分歧。
- **過載**:核心規則被歷史敘事擠沒了;優先刪除/遷移,而不是繼續往裡面加內容。
- **無門禁**:同一項違規第三次出現,說明散文式的約束已經不夠。依現場授權建議或實作 check/hook/test。

## 回報要求

每一條沒有自動修復的問題,都必須包含:

- 證據與規則出處;
- 所在範圍;
- 對使用者或協作流程的影響;
- 建議動作;
- 為什麼這次沒有自動執行。

不要用「發現 N 個問題」來取代判斷材料,也不要把範圍外的問題混進「專案已經乾淨」的結論裡。
