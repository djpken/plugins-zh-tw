# 變更影響矩陣

矩陣用來路由,不是要硬套固定檔名。先辨識專案現有的架構、接入、維運、決策與發布文件,再把對應的受眾更新到位。

## 先刪掉哪些雜訊

| 反模式 | 預設處理方式 |
|---|---|
| 「某日 X 上線,詳見 Y」塞在主規則最上方 | 現役的限制條件就地融合;純歷史內容遷到 git/changelog/事故文件 |
| 主規則裡抄了完整架構、評分公式或資料流 | 保留邊界與權威文件的指標,詳細機制放回 docs |
| 有多個版本都自稱「現役」 | 用程式碼開關、執行狀態與回退鏈裁決;歷史版本明確標示回退/退役 |
| 已完成的待辦事項仍列為開放項目 | 核實後刪除或改成目前的限制條件,不保留「已完成」的流水帳 |
| 單次事故長篇留在 memory 裡常駐 | 提煉可重複使用的教訓;機制放進 docs,過程放進 incident/git |
| 多處複製同一條規則 | 只保留一個權威真身,其他位置放簡短指標或直接刪除 |
| 「留著當歷史」但沒有真實讀者與用途 | 刪除;歷史內容需要用途、權威位置與檢索入口 |
| Agent 工作階段殘留:一次性計畫文件、除錯指令碼、`xxx_old`/`xxx_backup` 副本 | 有效內容併入正式文件;檔案列為刪除候選,經使用者確認後才清除 |

## 程式碼或執行狀態變化 → 知識面

| 變化 | 要核對的受眾面 |
|---|---|
| API / 路由 / 協定 | 對外接入合約、架構路由、認證、範例、consumer 文件、smoke |
| 環境變數 / provider / model | 範例 env、維運手冊、預設值權威來源、下游設定、成本/回退說明 |
| schema / 儲存欄位 | 資料模型、遷移與回滾、衍生/快取、讀寫邊界、測試 |
| 使用者流程 / 權限 / 導覽 | README/產品說明、架構權限、營運手冊、視覺驗收 |
| 評分 / 篩選 / 分群 / prompt | 現役演算法文件、閾值/開關、回測證據、回退鏈、呈現影響 |
| 服務 / 部署 / CDN / 邊緣節點 | 維運手冊、服務名稱、marker、快取、回滾、live acceptance |
| 背景工作 / 告警 | job 文件、排程、失敗處理、告警路由、決策面 |
| 退役 / 改名 / 下線 | 搜尋舊 symbol 的非歷史引用、consumer、rules、skills 與 memory;保留明確標示的歷史證據 |
| 發布流程 / 多 Agent 生命週期 | SOP、合併/部署指令碼、知識憑證、清場門禁、workspace audit |

## 受眾職責

新增或改變一項能力時,至少要判斷下列四種職責是否存在;不是要求一定要建立四個固定檔案:

1. **怎麼用**:README、API/整合指南、範例。
2. **怎麼運作**:architecture、schema、狀態機、設計邊界。
3. **怎麼維運**:runbook、環境變數、smoke、回滾、告警。
4. **目前狀態/歷史**:產品 changelog、release note、incident 或 git;只有專案規則/使用者明確要求時才寫 changelog。

如果同一份文件承擔多個職責,可以就地更新,不需要為了形式而拆成多份檔案。

## 記憶路由

| 記憶類型 | 處理方式 |
|---|---|
| 使用者偏好 / 反覆糾正 | 在平台允許且使用者授權時,保留簡短、可執行的條目 |
| 系統機制 | 畢業進權威 docs;memory 只留檢索指標 |
| 決策事件 | 只保留最終結論與仍然有效的原因;過程歸入 git/changelog |
| 已完成的開放項目 | 核實後刪除,不讓它繼續冒充計畫中的項目 |
| 相對時間 | 目前狀態改成絕對日期;歷史敘事裡的自然語言不機械式替換 |
| 重複或衝突 | 用目前程式碼/執行狀態裁決;無法裁決就保留衝突並標 pending |
| 機器產生的索引 | 不要直接編輯;寫下規定的輸入或候選,交給產生流程處理 |
| 長期未被引用 | 結合權威性與重複使用價值判斷;未被引用不是單獨的刪除理由 |

## 規則違規 → 動作

| 發現 | 動作 |
|---|---|
| 現場規則要求同源,但符號連結/匯入缺失 | 在授權範圍內補齊並驗證 realpath/load |
| 兩份獨立規則內容不同 | 若現場宣告能唯一裁決就合併;否則列為待決 |
| 有可執行程式碼但缺乏專案規則 | 預設建立最小規則檔(五要素、精簡);工作區有範本就依範本 |
| ignore 規則缺少安全紅線 | 在請求範圍與授權內直接補上,並驗證 tracked secrets |
| 命名違規、根目錄檔案雜亂 | 唯讀回報影響;搬移/重新命名/刪除通常列為待決 |
| 規則引用退役路徑/指令 | 在目前機器上唯一確認且沒有跨裝置疑慮時清除;否則回報 |
| 同一項違規反覆出現 | 用 check/hook/test 根治;是否自動實作依現場授權而定 |

## 跨專案檢查

以下任一為真時,就要搜尋實際的 consumer,而不是只改目前這個專案:

- 共用的 API、SDK、網域、認證、schema 或環境變數改變;
- 部署/邊緣層改變了下游可見的行為;
- 公用的 skill、指令碼或範本被多個專案引用;
- 目前專案的文件明確列出了依賴方。

唯讀方式發現 consumer,不代表獲准編輯它。先說明相依證據與影響範圍,再依任務與工作區規則決定下一步行動。
